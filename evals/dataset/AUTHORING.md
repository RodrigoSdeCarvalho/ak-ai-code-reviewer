# Authoring eval cases

This guide is for anyone (human or agent) adding a case to `evals/dataset/cases/`. Follow it literally: the validator enforces most of it, and the rest decides whether the case measures anything.

Two working examples live next to this file: `cases/seeded-template-01/` (a seeded bug) and `cases/clean-template-01/` (a correct change with a decoy). Copy one as a starting point.

## 1. What a case is

A case is one pull request. `before/` is the repository before the PR, `after/` is the repository after it, and `change.diff` is the diff the reviewer sees. The reviewer only ever sees `after/` and `change.diff`. Nothing else in the case directory (`case.yaml`, `fixed/`, `tests/`) is shown to it.

| Kind | What the PR contains | Ground truth | Has `fixed/` | Has `tests/` |
|---|---|---|---|---|
| `seeded` | A realistic feature or refactor that introduces 1 or 2 defects | `test-validated` | yes | yes |
| `clean` | A correct feature, refactor, rename or docs change | `none` | no | yes |
| `real` | A reverted bug fix from a public repository | `fix-derived` (or `test-validated` if you add a test) | yes | optional |

## 2. Directory layout

```
cases/<case_id>/
├── case.yaml          # metadata and labels (section 3)
├── before/            # repo state before the PR: only the files the case needs
├── after/             # repo state after the PR: what the reviewer reviews
├── change.diff        # GENERATED by the validator from before/ -> after/; never edit by hand
├── fixed/             # seeded/real only: ONLY the files that change once the defect(s) are fixed,
│                      #   at the same relative paths as in after/ (an overlay, not a full copy)
└── tests/test_case.py # seeded/clean (optional for real): pytest file, see section 6
```

- `<case_id>` is the directory name and must equal `id` in `case.yaml`. Use `seeded-<category>-NNN`, `clean-NNN` or `real-<project>-NNN` (for example `seeded-security-004`, `clean-012`, `real-httpx-002`).
- Paths inside `before/`, `after/` and `fixed/` are repo-relative: `after/shop/api.py` is the file `shop/api.py`. Use a real package layout with `__init__.py` files (for example `shop/`, `billing/`, `app/`).
- A file that the PR adds exists only in `after/`. A file that the PR deletes exists only in `before/`. Unchanged files that the code imports must be in both.
- No `__pycache__`, `.pyc`, or editor files. Text files only, UTF-8, LF line endings.

## 3. `case.yaml`

```yaml
id: seeded-logic-007
kind: seeded                       # seeded | clean | real
title: Page count floors a partial last page in the new list-orders endpoint
language: python
provenance:
  origin: authored                 # authored | reverted-fix
  source: null                     # real: "<repo URL> <fix commit sha> <commit date>"
  author: claude-opus-5-5 (agent), reviewed by Rodrigo
  created: '2026-10-23'            # quote dates
ground_truth: test-validated       # seeded: test-validated | clean: none | real: fix-derived
bugs:
  - id: b1
    file: shop/pagination.py       # repo-relative, as it appears in after/
    line_start: 39                 # 1-based line numbers in the after/ file
    line_end: 39
    severity: high
    category: logic
    description: >
      `total_pages = total // per_page` rounds down, so a partial last page is not counted
      (25 orders at 10 per page gives 2 pages instead of 3). Clients that follow `has_next`
      never see the remaining orders.
    must_find: true
notes: >
  PR purpose: add a paginated GET /customers/{id}/orders endpoint.
```

- Do not write `split` or `size_bucket`. `aireview eval split` assigns `split`; the validator computes `size_bucket`.
- `title` describes the PR plus, for seeded/real, the defect. It is never shown to the reviewer.
- `notes` (optional) holds the PR purpose and, for clean cases, the decoy (section 8).
- `description` states the defect and its runtime consequence plainly: what is wrong, which input triggers it, and what goes wrong. Write it before any model sees the case, and never soften it after seeing model output.
- Clean cases have `bugs: []`. Seeded and real cases have at least one bug. About a quarter of seeded cases should have 2 bugs (ids `b1`, `b2`), each in a different place, each fixed in `fixed/` and each caught by the test.
- `must_find: false` is for a real but secondary defect that a good reviewer may reasonably skip. Use it rarely.
- `tags` (optional, per bug) marks a label that may be out of the reviewer's reach: `unshown_context` when establishing the defect needs code the review prompt does not show (an unchanged file, or a part of a changed file over 600 lines, where only hunks are shown); `library_knowledge` when it needs knowledge of a third-party library's internals. Tagged bugs still count everywhere; they are also reported as their own slice (`slices.tag`). Prefer writing the case so that no tag is needed.
- The two template cases are pinned to `dev`: this guide prints the seeded template's bug and the clean template's decoy, so they must never be part of a gated or headline run.

## 4. The line-number contract

- `line_start` and `line_end` are **1-based line numbers in the post-change file** (`after/<file>`), inclusive.
- The labelled range must overlap a line that the diff changes (a `+` line, or for a deletion the nearest surviving line). The defect must be introduced by the PR under review, not something that was already there.
- Label the smallest range that pins the defect: usually the one line a fix would change. For a defect spread across lines (for example a lock taken on line 40 and never released on line 52), label the whole range.
- `fixed/` must change something within 3 lines of each labelled range. If the fix is elsewhere, the label is in the wrong place.
- Check numbers with `grep -n` on the `after/` file, never by counting by eye.

### Alternative locations (`alt_locations`)

Some defects have more than one place where a careful reviewer would legitimately comment on the same root cause. List the others under the bug, so a correct finding there is not scored as a miss plus a false positive:

```yaml
    alt_locations:                 # optional; same line contract as the label
    - file: shop/catalog.py        # e.g. the callee whose body does the expensive walk
      line_start: 58
      line_end: 60
```

- Use it for two-sided defects only: a loop in the caller and the callee that does the expensive work; a changed callee and the stale call site that now gets the wrong thing; the check and the act of a check-then-act; a value that is set and the code that overwrites it.
- Be conservative. A comment at the alternative must clearly be about the same root cause. Never add a generic spot (an import, a signature that is merely related, a docstring), a callee that is unchanged and correct for its other callers, or a range widened by a few lines just to be generous: findings within 3 lines of a location already match.
- Keep the label as the primary location: it is where `fixed/` changes code and what `description` explains. An alternative may be on unchanged lines, but it must be in a file of `change.diff` (findings on other files are out of scope and could never match it).
- The judge sees the alternatives as "Also reportable at: …" and the code around the one nearest the finding. Decide them from the code and the diff, never from model output.

## 5. Making a realistic PR

The reviewer is graded on PRs that look like real work. A case where the defect is the whole diff measures nothing.

1. **The change has a purpose.** Write it down in `notes` first: "add a list endpoint", "move rate limits to config", "switch to a connection pool", "rename `user_id` to `account_id`". The diff must make sense as that PR.
2. **The defect is part of the change, not a separate edit.** It is a mistake someone could plausibly make while doing that work: a boundary written wrong in new pagination code, an exception swallowed in a new retry loop, a file handle opened in a new export function without being closed, a query built with string formatting in a new search filter.
3. **Fresh code.** Write the code for this eval. Do not copy well-known open-source code or textbook bug examples; a model may have memorised them.
4. **Context.** Include enough of the repository (`before/` = `after/` for unchanged files) that the defect can be judged from what is shown: the caller, the data model, the config. Keep each `after/` file between 40 and 400 lines. Small helper files such as `__init__.py` may be shorter.
5. **No hints.** No comments, names, strings, docstrings or file names that point at the defect. Code in a seeded case reads like the author believed it was correct. The validator rejects added lines that contain (case-insensitive): `bug`, `buggy`, `fixme`, `seeded`, `todo: fix`, `vulnerab`, `inject`, `off-by-one`, `race condition`, `leak`. Avoid synonyms that do the same job ("intentionally", "careful here", "known issue").
6. **Unique.** No two cases may have identical `after/` trees.
7. **Diff size.** Aim for the dataset mix of 40% S, 40% M, 20% L (section 9). A large diff with a small defect is the hardest and most realistic kind.

## 6. Test rules (`tests/test_case.py`)

- **Seeded:** the tests must **fail on `after/`** (pytest exit code 1: an assertion failure, not an import or collection error) and **pass on `after/` with `fixed/` overlaid**. At least one test must target each bug.
- **Clean:** the tests must **pass on `after/`**. They pin the behaviour the PR claims, including the decoy, so they prove the change is correct.
- **Real:** optional. If present, they follow the seeded rules and `ground_truth` may be `test-validated`.
- Import the code as the repository would, from the repo root: `from shop.pagination import paginate`. The harness copies `after/` to a temp directory, overlays `fixed/` when asked, and runs pytest with that directory as the working directory and on `PYTHONPATH`. `tests/` is copied to a separate directory, so do not import from `tests/` or use relative paths to case files.
- Deterministic and offline: no network, no real clock (pass fixed `datetime` values), no randomness without a fixed seed, no sleeping longer than a few milliseconds. Concurrency tests must be reliable (use barriers or many iterations, never luck).
- Standard library plus `pytest` only. Whole file under 5 seconds (the harness kills it at 60).
- Do not write files outside pytest's `tmp_path`.

## 7. Severity rubric

| Severity | Use when the defect causes |
|---|---|
| `critical` | a security breach, data loss or corruption, or a crash on the main path |
| `high` | wrong results on a common path |
| `medium` | wrong results on an edge path, or degraded behaviour (slow, retries too often, poor error message on a real failure) |
| `low` | a minor problem: cosmetic output, a rarely visible inconsistency |

Pick the severity from the consequence for a real user of the code, not from how hard the defect is to spot.

## 8. Categories

Use exactly one of `aireview.models.Category` per bug:

| Category | Defects of this kind |
|---|---|
| `logic` | wrong computation or control flow: boundaries, conditions, wrong variable, wrong operator, wrong ordering |
| `security` | injection (SQL, shell, path), missing authorisation or authentication checks, secrets exposure, unsafe deserialisation, weak crypto or randomness |
| `error_handling` | swallowed or over-broad exceptions, missing error paths, wrong exception type, partial failure leaving bad state, retries that never stop |
| `concurrency` | unsynchronised shared state, check-then-act, deadlocks, async misuse (blocking calls in a loop, missing `await`) |
| `resource` | handles, connections, locks or temp files not released; unbounded growth of caches or queues |
| `performance` | needless quadratic work, N+1 queries, repeated expensive calls in a loop, loading everything into memory |
| `api_contract` | breaking a caller's expectations: changed return type or shape, changed defaults, wrong status code, mutated arguments, wrong units |
| `maintainability` | defects in clarity rather than behaviour. Do not seed these: the eval only labels behavioural defects |

Gated slices need at least 4 seeded cases each: `logic`, `error_handling`, `security`, and `state` (`resource` and `concurrency` together). Spread the rest over `performance` and `api_contract`. The primary category of a case is the category of its first bug.

### Clean cases and decoys

A clean case measures false alarms, so make it tempting. Each clean case should contain at least one **decoy**: code that looks suspicious but is correct. Examples: `bisect_left` on upper-inclusive tiers; `range(len(xs) - 1)` for pairwise comparisons; a bare-looking `except` that re-raises; string formatting on a value that is already an `int`; a lock released in a `finally` far from where it is taken; a mutable default argument that is never mutated. Describe the decoy in `notes` and pin its behaviour in the tests. Clean changes still need a plausible purpose, the same realism as seeded cases, and no defects at all. If you notice one while writing, either fix it or turn the case into a seeded one.

## 9. Size buckets

The validator counts the `+` and `-` lines in `change.diff` (headers excluded): **S** < 30, **M** 30 to 120, **L** > 120. It writes the bucket to `case.yaml` when run with `--write`.

## 10. Validator commands

Run from the repository root:

```bash
aireview eval validate-dataset --case <case_id> --write   # regenerate change.diff + size_bucket, refresh manifest, run all checks
aireview eval validate-dataset --case <case_id>           # check only (what CI does), including the tests
aireview eval validate-dataset --fast                     # all cases, skip running tests
aireview eval validate-dataset                            # full check of the dataset (exit 1 on any problem)
aireview eval split                                       # assign dev/test to cases without a split (maintainers only)
```

The validator checks: schema; `id` equals the directory name; `change.diff` equals a fresh `before/` to `after/` diff; `size_bucket`; `ground_truth` fits the kind; every bug's file exists in `after/`, its range is within the file and overlaps a changed line; every alternative location is within an `after/` file that the diff touches; `fixed/` changes something near each label; leakage words in added lines and file names; `fixed/` files exist in `after/` and differ from it; clean cases have no bugs and no `fixed/`; the test behaviour in section 6; no duplicate `after/` trees; and that `manifest.yaml` is up to date. Fix every problem it reports; do not weaken a check to make a case pass.

## 11. Checklist before you finish a case

- [ ] `notes` states the PR purpose (and the decoy, for clean cases).
- [ ] The defect is part of the change and is not hinted at anywhere in `after/`.
- [ ] `description` states the defect, the trigger and the consequence.
- [ ] Line numbers checked with `grep -n` against `after/`.
- [ ] `aireview eval validate-dataset --case <id> --write` reports `ok`.
